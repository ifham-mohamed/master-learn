Warehouse Dispatch learning plan

Study five hours per selected day. Write your own code and tests. Keep a short record of what you ran, what happened, and what comes next.

Start with JA05 · Project requirements · Excel tracker

Phases

  1. Terminal and domain · Create, find and summarize shipments in the terminal.
  2. Spring and React · Create and find shipments in the browser through a tested HTTP API.
  3. PostgreSQL and reservation · Persist shipments and prove that concurrent requests cannot oversell stock.
  4. Secure warehouse workflow · Sign in, reserve, pick and dispatch with tested permissions and balances.
  5. Operational readiness · Measure the application, test safe retries, and rehearse staging recovery.
  6. Independent demonstration · Repeat a change under time and give a demo another person can run.

    A boundary test catches a forbidden dependency. The last-unit and rollback tests still pass. State which data is authoritative and how you would roll back a split.

  2. 2. Publish dispatch events through RabbitMQ · after B19

    Record a versioned DispatchConfirmed event in a PostgreSQL outbox in the same transaction as dispatch. Publish through RabbitMQ and wait for broker confirmation. The consumer commits a deduplicated result before acknowledging. Cap retries, route failed messages to a dead-letter queue, and retain an event archive for rebuilding projections. Compare a RabbitMQ work queue with a retained Kafka log, using partition keys and consumer offsets to reason about ordering and replay.

    Roll back a dispatch, stop the broker after commit, interrupt the publisher before marking a send, and replay a poison message. Show zero events for the rollback, eventual delivery for the committed event and one consumer effect under redelivery.

  3. 3. Extract a Tracking microservice · after B20

    After the broker lab, extract the read-oriented tracking projection. Give it its own PostgreSQL database and schema migrations, API and release. Update it from versioned events without reading the dispatch tables. Document eventual consistency, projection rebuild, stale-state UX, and service authentication. Model compensation for a hypothetical cross-service reservation as a separate design exercise.

    Take Tracking down while dispatch continues. Restart it and rebuild a clean projection from the retained event archive. Reconcile results. Run API contract tests, deploy Tracking independently, and rehearse routing traffic back to the original tracking view.

  4. 4. Release a Tracking micro-frontend · after B20

    After the Tracking service lab, separate the read-only Tracking routes into an independently built React frontend. Compose at the route boundary. Define shared navigation, session behavior, accessibility and API contracts. Compare this with keeping feature modules in one React build.

    Deploy and roll back the Tracking frontend without rebuilding Dispatch. Verify keyboard navigation, direct URLs, sign-out, API failure fallback, and bundle size before and after the split.

  5. 5. Prove the distributed system can recover · after B20

    Set a workload and targets for latency, errors and projection lag. Trace request and event IDs across components. Exercise rate limits, stale reads, backlog pressure, restore, and rollback. Compare container deployments and orchestration using the needs you measured.

    Save p95 latency, error rate, oldest queued event, recovery time and restored-data checks. Test a failed release and write a runbook another person can follow.
